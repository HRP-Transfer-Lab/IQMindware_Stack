## 1. Purpose

This document defines how the research-grade Cognitive Workflow Ontology should be translated into a useful, commercially effective and claims-safe website experience.

The ontology must remain scientifically strict. The public website must remain constructive and action-oriented.

The website should therefore use the ontology to produce:

```text
what this workflow demands
→ which cognitive functions are relevant
→ which available IQ Mindware apps address those functions
→ which workflow supports should be considered alongside training
→ how progress should be measured
→ what evidence is established, emerging or still being generated
```

The website must not reduce the route to a binary verdict such as:

```text
proven
or
no evidence
```

The commercial role of the ontology is to configure the strongest defensible route, not to veto every use that lacks a workflow-specific randomised controlled trial.

---

## 2. Governing principle

# **Return a route, not an evidence verdict**

A website result should lead with:

1. the relevant workflow demand;
2. the available intervention route;
3. the workflow changes that should be tested alongside it;
4. the outcome plan;
5. the current evidence boundary.

Use this sequence:

```text
POSITIVE BASIS
Why the route is relevant

↓

AVAILABLE INTERVENTION
What can be used now

↓

WORKFLOW SUPPORT
What should change around the person or task

↓

MEASUREMENT PLAN
How progress will be tested

↓

EVIDENCE BOUNDARY
What has not yet been established
```

Do not lead with the evidence gap.

### Poor public output

> There is no direct evidence that WM Coach improves AI-output verification.

### Required public output

> This workflow places high demands on maintaining source–claim bindings and controlling attention during verification. WM Coach Binding Memory and Attention Coach target relevant foundational functions. Direct improvement in AI-output verification has not yet been established, so the recommended organisational route includes a separate verification task and a bounded pilot.

Both statements are scientifically honest. Only the second is commercially useful.

## 3. Keep the research and commercial layers separate

The scientific ontology and the website commercial overlay have different responsibilities.

| Research ontology | Website commercial overlay |
|---|---|
| Defines the workflow and stage | Selects the public example and wording |
| Codes demands and frictions | Assembles the user-facing explanation |
| Maps demands to cognitive functions | Applies current product availability |
| Records independent evidence dimensions | Translates them into public evidence labels |
| Identifies person, task, team and system loci | Recommends a combined cognitive and workflow route |
| Defines suitable outcomes | Selects the current pilot measurement package |
| Records governance profile | Determines eligibility and CTA |
| May identify an unavailable function | Offers the nearest available foundation and labels the target module in development |

The ontology must not be edited to make a current product appear more relevant.

The website must not claim that a theoretical mapping is an established applied effect.

---

## 4. Evidence should be layered, not collapsed

The canonical research confidence dimensions are:

```text
W — Workflow representation
D — Cognitive-demand mapping
F — Cognitive-function mapping
P — Protocol fit
O — Workflow outcome evidence
I — Implementation readiness
```

These dimensions must remain separate internally.

The public website should translate them into a short evidence panel rather than exposing codes such as `W2-D1-F1-P1-O0-I1`.

### Recommended public dimensions

| Public field | Internal basis | Example wording |
|---|---|---|
| **Workflow basis** | W | Practitioner-confirmed |
| **Demand mapping** | D + F | Evidence-informed |
| **Current app fit** | P | Relevant foundational protocol available |
| **Applied outcome evidence** | O | To be tested in a bounded pilot |
| **Deployment status** | I + governance | Pilot-ready |

### Example

```text
Workflow basis:
Practitioner-confirmed

Cognitive-demand mapping:
Evidence-informed

Current app fit:
Relevant foundational protocols available

Applied outcome evidence:
Not yet established for this workflow

Deployment status:
Available for a bounded non-clinical pilot
```

This is more informative than one overall evidence score.

## 5. Commercial route statuses

Use a controlled set of public statuses.

| Status | Meaning | Typical CTA |
|---|---|---|
| **Available now** | The app or measurement route exists and the intended use is permitted | Start the app / build my route |
| **Evidence-informed route** | The workflow, demand and function mapping have a defensible research basis | View the route |
| **Pilot-ready** | The route has defined users, workflow placement, outcomes and governance, but lacks direct applied-effect evidence | Discuss a pilot |
| **Pilot-supported** | Initial applied evidence supports selected outcomes | Review results / expand pilot |
| **Validated in workflow** | Controlled or replicated evidence supports the intended applied use | Deploy / discuss integration |
| **Research collaboration** | The use is health-related, high-stakes or depends on a module still under development | Discuss a research partnership |
| **Not currently suitable** | No defensible route, outcome plan or governance basis exists | View alternatives / contact us |

Most early organisational routes should be allowed to carry a combination such as:

```text
AVAILABLE NOW
+
EVIDENCE-INFORMED
+
PILOT-READY
```

Lack of direct workflow-effect evidence does not automatically mean that a route is unsuitable for a bounded pilot.

---

## 6. Minimum commercial evidence floor

A route may appear publicly as **evidence-informed and pilot-ready** when all of the following conditions are satisfied:

1. The workflow stage is documented, practitioner-confirmed or sufficiently represented by an approved archetype.
2. The important cognitive demands are supported by relevant literature, structured task analysis or expert review.
3. The mapping to the proposed cognitive function is plausible, reviewable and does not ignore strong alternative explanations.
4. At least one currently available app addresses a relevant foundational function.
5. The route includes a separate cognitive, functional or workflow outcome measure.
6. The governance profile permits the proposed use.
7. The approved copy does not imply that workflow benefit is already established.
8. The route considers task/interface, team/process and organisation/system changes alongside person-level training.

Direct workflow-effect evidence is required before the website may say that the route **improves** the applied workflow outcome.

---

## 7. When the system should abstain

The website should return **Not currently suitable** or **Research collaboration** only when one or more of these conditions apply:

- the workflow cannot be represented adequately;
- the cognitive mapping is too speculative to support even a bounded route;
- no available app addresses a relevant foundational function;
- the requested output implies diagnosis, treatment or another high-stakes claim without an approved protocol and governance route;
- a meaningful outcome cannot be measured;
- the main problem is clearly organisational and cognitive training would misdirect attention;
- the organisation seeks prohibited consequential uses such as recruitment, promotion, disciplinary scoring or covert productivity ranking;
- the available evidence or data quality is insufficient even to define a testable pilot.

Abstention is a safety and integrity mechanism. It should not become the default response to every absence of direct trial evidence.

## 8. Use a curated launch catalogue

The first production release should not accept arbitrary free-text organisational problems and attempt to route all of them.

Launch with a curated set of workflow stages for which the ontology contains:

```text
documented workflow
approved demand profile
approved friction signatures
current app coverage
workflow-support recommendations
defined outcomes
governance profile
approved public copy
```

Recommended initial workflow catalogue:

1. Reviewing AI-generated reports or analyses
2. Integrating sources into professional or academic work
3. Recovering complex work after interruption
4. Screening research or case material against criteria
5. Maintaining project dependencies and hand-offs
6. Focused study under distraction and time pressure
7. Monitoring repetitive information streams
8. Establishing a baseline and following up cognitive performance

Open-ended routing can be added only after ontology coverage, abstention rules and held-out route testing are sufficiently mature.

## 9. Mandatory route-result structure

Every website route should contain the following sections in this order.

### 9.1 Route heading

Example:

> **A relevant foundational route is available**

Other approved headings:

- Evidence-informed route
- Available for a bounded pilot
- Measurement-first route
- Research collaboration route
- Not currently suitable

### 9.2 Workflow explanation

Explain what the person is trying to accomplish and where the cognitive demand arises.

Example:

> Reviewing AI-generated material requires relevant information to be selected while claims remain attached to their sources and contexts. The verification stage also requires the reviewer to resist plausible but unsupported conclusions.

### 9.3 Cognitive-support route

Show only currently available modules as available.

Example:

```text
G Track baseline
→ Attention Coach Signal
→ WM Coach Binding Signal
→ G Track follow-up
→ delayed re-check
```

Where the closest target module is in development, state this explicitly:

```text
Closest target function:
Reasoning Evidence — in development

Current available foundation:
Attention Signal + WM Binding Signal
```

### 9.4 Workflow-support route

The result must also recommend relevant non-training supports.

Example:

```text
protected verification window
→ visible source–claim ledger
→ separate drafting and checking stages
→ explicit release checkpoint
```

### 9.5 Evidence panel

Display:

- workflow basis;
- cognitive-demand mapping;
- current app fit;
- applied outcome evidence;
- deployment status.

### 9.6 Outcome plan

Select outcomes at more than one level where feasible:

```text
app learning
cognitive measure
functional task
workflow outcome
implementation outcome
delayed outcome
```

### 9.7 Current evidence boundary

Use one concise statement.

Example:

> The current apps target relevant foundational functions. Improvement in AI-output verification itself has not yet been established.

### 9.8 Commercial CTA

Select the CTA from the governance and maturity status:

```text
Start my route
Take a baseline
Discuss a bounded pilot
Download the route summary
Discuss a research collaboration
```

## 10. Public evidence wording

Use a positive evidence ladder.

```text
PUBLISHED FOUNDATION
The underlying task or paradigm has a research basis.

↓

IMPLEMENTED PROTOCOL
The app operationalises the target function.

↓

WORKFLOW RATIONALE
The function is relevant to a defined workflow demand.

↓

PILOT MEASUREMENT
The applied outcome will be tested separately.

↓

DEPLOYMENT EVIDENCE
Results determine whether the route is retained, revised or stopped.
```

### Recommended public labels

- Published foundation
- Established paradigm basis
- Initial controlled evidence
- Evidence-informed mapping
- Relevant foundational fit
- Under staged validation
- Pilot-ready
- Pilot-supported
- Applied outcome to be tested
- Direct workflow benefit not yet established

### Avoid

- No evidence, when a defensible foundational route exists
- Scientifically proven
- Clinically proven
- Validated for this workflow, unless this is literally true
- Improves focus, working memory or reasoning without specifying the outcome and evidence
- Personalised, unless the route genuinely adapts to the individual or workflow

## 13. Example: AI-output verification

### Result heading

# **An evidence-informed verification route is available**

### Why this workflow is demanding

Reviewing AI-generated material requires:

- selecting relevant information among plausible detail;
- preserving which source and context supports each claim;
- maintaining contradictions and dependencies while reviewing;
- resisting premature release because the output appears fluent;
- committing when the verification threshold is sufficient.

### Current cognitive route

```text
G Track baseline
→ Attention Coach Signal
→ WM Coach Binding Signal
→ G Track follow-up
→ delayed re-check
```

### Workflow supports to test

```text
protected verification period
→ source–claim ledger
→ separate drafting and verification
→ explicit release checkpoint
→ disconfirmation prompt
```

### Evidence profile

| Evidence layer | Public status |
|---|---|
| Workflow demand | Documented and expert-reviewable |
| Attention mapping | Evidence-informed |
| Source-binding mapping | Established paradigm rationale |
| Current app implementation | Under staged validation |
| AI-verification improvement | To be tested in the pilot |

### Pilot outcomes

- unsupported claims detected;
- source-attribution errors;
- review time;
- rework;
- G Track attention change;
- G Track binding change;
- delayed persistence.

### Boundary

> Current apps address relevant foundational attention and binding functions. Direct improvement in AI-output verification has not yet been established.

### CTA

> **Discuss a verification pilot**

## 15. Individual versus organisation outputs

### Individual route

The result may lead directly to an app when:

- the use is non-clinical;
- the user chooses the goal;
- the available app has a relevant foundational fit;
- no consequential organisational decision is attached to the result.

Typical CTA:

```text
Take G Track
Start Attention Coach
Start WM Coach
```

### Organisation route

The result should usually lead to a bounded pilot when:

- a workflow outcome is being targeted;
- the route combines training and workflow changes;
- aggregate reporting is required;
- applied-effect evidence is still being generated.

Typical CTA:

```text
Discuss a pilot
Download route summary
```

### Health or high-stakes route

Health, clinical-adjacent and other high-stakes uses should resolve to:

```text
Research collaboration
Partner-led protocol development
Governance review
```

They should not resolve to a consumer treatment recommendation.

## 16. Website implementation rules

The route engine should always attempt to populate:

1. the best-supported workflow explanation;
2. the closest relevant cognitive functions;
3. the currently available protocol route;
4. the target functions still under development;
5. the person-versus-system intervention balance;
6. a separate outcome plan;
7. the public evidence panel;
8. the required caveat;
9. the permitted CTA.

It should not calculate one opaque percentage match.

Recommended internal output:

```text
workflow relevance
friction match
function fit
protocol coverage
evidence maturity
governance eligibility
```

Recommended public output:

```text
Relevant workflow demands
Available route
Workflow supports
Evidence status
Measurement plan
Current limitation
Next step
```

## 17. Validation of the commercial pathway

The commercial pathway itself should be tested.

### Required route tests

- a strong available Attention route;
- a strong available Relational Memory route;
- a strong available Binding Memory route;
- a combined Attention + WM route;
- a target function in development with a partial available foundation;
- a workflow-design problem where training is secondary;
- a health pathway requiring research collaboration;
- a prohibited consequential-use request;
- an insufficiently represented workflow;
- an individual measurement-only route.

### Review questions

For every result, reviewers should ask:

```text
Does the result explain the workflow rather than merely relabel the complaint?

Does it offer the strongest currently available route?

Does it distinguish training from workflow redesign?

Does it preserve the evidence boundary without leading with failure?

Does it provide a measurable next step?

Is the CTA appropriate to the governance profile?
```

### Commercial success measures

Track:

- route-builder completion;
- proportion receiving a meaningful route;
- evidence-panel engagement;
- baseline starts;
- app starts;
- route-summary downloads;
- pilot enquiries;
- conversion from enquiry to bounded pilot;
- proportion of routes later revised following evidence review.

Do not optimise the route engine simply to maximise positive recommendations.

---

## 18. Forbidden commercial patterns

The website must not:

- convert every workflow problem into individual cognitive training;
- imply that a foundational function mapping proves an applied outcome;
- hide unavailable target modules;
- use one global “science-backed” badge;
- label users or employees with clinical, deficit or brain-state language;
- rank individuals for employment, education or disciplinary purposes;
- present G Track as an official IQ test;
- imply that matrix-reasoning change is guaranteed;
- claim that workflow benefit is established when it is only proposed for a pilot;
- use the absence of a workflow-specific trial to erase valid task, construct and protocol evidence.

---

## 19. Commercial proposition

The website should not promise:

> Every route is already proven.

It should promise:

> **Every route has an explicit evidence basis, a defined uncertainty, a measurable outcome and a plan for becoming better supported.**

Commercially, the ontology should support this loop:

```text
identify a credible workflow problem
→ locate the relevant cognitive and workflow mechanisms
→ configure the strongest available route
→ specify what is known
→ define what should be tested
→ convert the result into an app pathway or bounded pilot
→ use the result to retain, revise or retire the route
```

This is the appropriate commercial translation of an evidence-backed precision cognitive workflow platform.

---

## 20. Final decision rule

When evidence is incomplete, the route engine should ask:

```text
Is there enough evidence to define a relevant foundational route,
a claims-safe explanation and a measurable pilot?
```

If yes:

```text
return an evidence-informed or pilot-ready route
```

If no:

```text
abstain, redirect or offer research collaboration
```

The purpose of scientific caution is to define the right commercial next step—not to turn every emerging application into a “no evidence” page.
